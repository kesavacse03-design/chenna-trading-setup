Canary Plan: CTS Backtest Engine

Goal
----
Safely roll out changes to the backtest engine with minimal risk to users by running a controlled set of production-like backtests and validating key metrics.

Prerequisites
-------------
- Monitoring in place (Prometheus scrape of `/metrics`) and alert rules configured.
- Secrets in Vault and run workers able to fetch them.
- A canary deploy namespace (or isolated host) with the same configuration as production but limited capacity.

Phased rollout
--------------
1. Dry-run (CI): run contract tests + perf smoke (50 symbol) against the change in CI. Must pass.
2. Canary small: run 5 real non-critical backtests (low risk) in canary namespace for 30 minutes while monitoring:
   - backtest_run_errors_total == 0
   - p99 per-symbol latency stable (within 20% of baseline)
   - RSS and CPU within expected limits
3. Canary widen: if above passes, run 25 backtests for 60 minutes; monitor same metrics and error budgets.
4. Gradual traffic shift: move 10% of scheduled runs to canary for 2 hours; if stable, increase to 50% then 100%.

Acceptance criteria
-------------------
- No job schema validation failures.
- backtest_run_errors_total not exceeding baseline + 1%.
- p99 per-symbol latency within 20% of baseline.
- No OOMs or host-level restarts.

Rollback plan
-------------
- If any acceptance criterion fails, immediately stop new jobs, revert deployment, and re-run failed canary jobs on previous version.
- Keep artifact retention long enough to compare results between versions.

Post-Canary
-----------
- Run a 2-hour observation window after full rollout with stricter alerting.
- Document any anomalies and update playbooks.
